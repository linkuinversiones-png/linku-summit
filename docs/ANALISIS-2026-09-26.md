## 2. Qué es y cómo está construido

Landing bilingüe (ES/EN) del evento **LINKU CAPITAL SUMMIT 2026** (5 y 6 de
octubre de 2026, Country Club Medellín), con venta de entradas y panel de
administración.

| Pieza | Tecnología |
|---|---|
| Framework | Next.js 15 (App Router) + React 19 + TypeScript |
| Estilos | Tailwind CSS 3 + Framer Motion |
| Datos, login y archivos | Supabase (Postgres + Auth con código OTP + Storage) |
| Pagos | Wompi (Web Checkout por redirect) |
| Acreditación de asistentes | InContacto (API) |
| Correos | Resend |
| Hosting | Cloudflare Workers vía `@opennextjs/cloudflare`; publicación automática desde `main` con GitHub Actions (desde 2026-09-26) |

### Mapa de carpetas

| Carpeta | Qué contiene |
|---|---|
| `app/[locale]/` | Páginas públicas: portada, checkout, login, `/me` (mis boletas), directorio de eventos |
| `app/admin/` | Panel interno (solo `profiles.role = 'admin'`): agenda, entradas, cupones, cortesías, órdenes, speakers, sponsors, ajustes, InContacto |
| `app/api/` | Webhook de Wompi, validación de cupones, estado de órdenes, cerrar sesión |
| `components/sections/` | Cada sección de la portada (Hero, Agenda, Speakers, Tickets, FAQ…) |
| `components/ui/` | Botones, tarjetas, contador y otras piezas reutilizables |
| `content/es`, `content/en` | **Textos del sitio** en JSON (títulos, FAQ, agenda de respaldo…) |
| `content/directorio/eventos/` | Fichas en Markdown del directorio de eventos |
| `lib/` | Lógica: Supabase, Wompi, órdenes, cupones, QR, correos, i18n, SEO |
| `supabase/migrations/` | 17 migraciones SQL de la base de datos |
| `scripts/` | Migraciones, configuración de Auth, datos de prueba |
| `docs/` | Documentación (deploy, handoff, este análisis, registro de cambios) |
| `.github/workflows/` | Publicación automática a Cloudflare en cada push a `main` |

### Dónde se editan las cosas más comunes

- **Textos fijos de la portada:** `content/es/*.json` y su par en `content/en/`.
  Siempre cambiar los dos idiomas.
- **Speakers, sponsors, entradas, agenda, cupones:** se administran desde
  `/admin` (viven en Supabase); los JSON de `content/` son respaldo.
- **Diseño de una sección:** `components/sections/<Sección>.tsx`.
- **Colores y tipografías:** `tailwind.config.ts` y `app/globals.css`.

### Flujo de compra (resumen)

1. `/checkout?tier=<slug>` → formulario de comprador (sin registro).
2. `startGuestCheckout` crea la orden `pending` y redirige a Wompi con firma
   de integridad (el monto no se puede alterar).
3. Wompi llama a `/api/webhooks/wompi` → se valida el checksum → orden `paid`
   → `fulfillPaidOrder` emite boleta con QR firmado, redime cupón, suma cupo
   y registra en InContacto.
4. Si un cupón deja el total en $0, la orden nace pagada (cortesía) y no pasa
   por Wompi.
5. El comprador luego inicia sesión por OTP y `claimMyOrders` le asocia sus
   órdenes por email.

## 4. Hallazgos en detalle

### 4.1 🔴 Llaves de producción expuestas en chat

El 2026-09-26 se compartieron por chat las llaves reales de Wompi
(producción), `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ACCESS_TOKEN`, Resend,
InContacto y `QR_HMAC_SECRET`.

**Recomendación:** rotar Wompi, Service Role, Access Token y Resend desde cada
panel y actualizar los secrets del Worker (ver `docs/DEPLOY.md`).
⚠️ **No rotar `QR_HMAC_SECRET`** sin plan: invalida todos los QR ya emitidos.
En adelante, compartir llaves por un gestor de contraseñas, no por chat, y
para desarrollo local usar solo las llaves públicas de Supabase o llaves
`pub_test_` de Wompi.

### 4.2 🔴 Dependencias vulnerables

`npm audit --omit=dev` reporta, entre otras:

- **next 15.5.19 — crítica:** DoS y SSRF en Server Actions. El sitio usa Server
  Actions (checkout, admin), así que aplica. Hay versión corregida.
- **postcss, sharp, undici, ws, nanoid, brace-expansion, wrangler/miniflare —
  altas:** todas tienen arreglo con `npm audit fix`.
- **xlsx — alta, sin arreglo en npm:** se usa solo para *generar* el Excel de
  `/admin/orders/export` (no lee archivos subidos), así que el riesgo real es
  bajo. Si se quiere eliminar, SheetJS publica versiones nuevas en su propio
  CDN, o se puede cambiar a `exceljs`.

**Recomendación:** `npm audit fix`, `npx tsc --noEmit`, `npm run build`,
probar checkout en local y luego desplegar.

### 4.3 🟠 `claimMyOrders` usa `ilike` con el email sin escapar

`app/[locale]/checkout/actions.ts:222-233`. En Postgres, `ilike` trata `_` como
"cualquier carácter". Alguien con la cuenta `jo_n@gmail.com` (email válido)
podría quedarse con las órdenes y boletas de `john@gmail.com` si esas todavía
no estaban asociadas a un usuario.

**Recomendación:** escapar `%`, `_` y `\` antes del `ilike`, o comparar con
`.eq()` usando el email en minúsculas (el checkout ya lo guarda así).

### 4.4 🟠 Boleta duplicada con eventos simultáneos

`tickets_issued.order_id` tiene índice pero **no restricción única**
(`0003_orders_tickets_coupons.sql:59`). `fulfillPaidOrder` revisa "¿ya existe
boleta?" y luego inserta; si Wompi entrega dos eventos APPROVED casi al mismo
tiempo, ambos pueden pasar el chequeo y emitir dos boletas (y sumar dos veces
el cupo).

**Recomendación:** migración nueva con
`unique (order_id)` en `tickets_issued` (revisando antes que no haya
duplicados) y tratar el error `23505` como "ya existía", igual que ya se hace
con `coupon_redemptions`.

### 4.5 🟡 El webhook no verifica el monto

`app/api/webhooks/wompi/route.ts`. La firma de integridad del checkout ya
impide alterar el monto, así que es defensa adicional: comparar
`amount_in_cents` con `order.total_cop * 100` antes de marcar `paid`, y dejar
nota en la bitácora si no coincide.

### 4.6 🟡 Otros menores

- **`sold_count` no atómico** (`lib/orders/fulfill.ts`): el propio código lo
  reconoce; aceptable para el volumen del evento. Se podría pasar a un
  `rpc` que haga `sold_count = sold_count + 1`.
- **`components/seo/JsonLd.tsx`** mete `JSON.stringify` dentro de `<script>`
  sin escapar `<`. Si un texto administrado contuviera `</script>` rompería la
  página. Solo lo pueden editar admins → riesgo bajo. Arreglo de una línea:
  `.replace(/</g, '\\u003c')`.
- **`docs/HANDOFF.md` desactualizado:** dice Next 14, ePayco y Vercel; hoy es
  Next 15, Wompi y Cloudflare. `docs/DEPLOY.md` sí está al día.
- **Sin README** en la raíz.
- **Sin pruebas automáticas.** Lo más valioso para empezar: pruebas de
  `lib/wompi/signatures.ts`, `lib/coupons.ts` y `fulfillPaidOrder`.

## 5. Lo que está bien hecho (para no romperlo)

- Firma de integridad de Wompi y checksum del webhook con `timingSafeEqual`.
- Service Role solo en servidor; el admin valida rol en `app/admin/layout.tsx`.
- 76 políticas/ajustes de RLS en las migraciones.
- Entrega de órdenes centralizada en `fulfillPaidOrder`, sin excepciones que
  hagan perder un pago; redención de cupones idempotente.
- URL de retorno a Wompi derivada del host real (lección aprendida documentada
  en `DEPLOY.md`).
- Bitácora de cambios de estado de cada orden (`order_status_log`).
- SEO: canonical sin prefijo `/es`, redirect apex → www, sitemap, JSON-LD.
